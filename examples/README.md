# 案例

> 以下为匿名化处理后的真实测试案例，展示本工具包在不同场景下的使用方式和产出。

## 案例 1：灰盒 — 某健康检测平台

**背景**：内部系统，有完整的接口文档（小程序端、台式机端、后台管理端三份 Markdown 文档）。

**模式判定**：`materials/` 含三份接口文档 → 灰盒模式。

**P0 产出**：
- 从文档提取 60+ 接口，按角色分为普通用户/操作员/管理员三层
- 识别出签名+加密网关层，从前端 JS 逆向获取算法和公钥
- 发现未鉴权接口 5 个，含大模型 API Key 下发接口

**P1 方案**：98 条测试用例，覆盖认证、授权、敏感数据、注入、业务逻辑、第三方组件。

**P2 执行**：
- 发现 8 个漏洞（1 严重 + 4 高 + 2 中 + 1 低）
- 最严重：DeepSeek API Key 未授权泄露
- 最危险的越权：操作员账户通过设备 ID 单因子登录可被接管

**P3 报告**：输出完整报告（8 页）+ 一页摘要，交付开发团队。

**耗时**：约 2 天（含复测验证）。

## 案例 2：黑盒 — 某电商 API

**背景**：仅有目标 URL，无任何内部文档。

**模式判定**：`materials/` 为空 → 黑盒模式。

**P0 产出**：
- 前端 JS 审计发现 15 个接口路径
- 响应头探测发现 Spring Boot + Nginx
- Swagger 未暴露，但 Actuator /health 可达
- 从报错信息推断出部分参数名

**P1 方案**：基于发现的 15 个接口制定 40 条测试用例。

**P2 执行**：
- 发现 JWT token 可伪造（alg:none）
- 用户 ID 可遍历导致信息泄露
- 支付回调签名缺失

**P3 报告**：输出黑盒测试报告，标注所有发现均来自外部探测。

**耗时**：约 3 天（大部分时间花在接口发现和参数推断上）。

---

## 对比

| | 灰盒（案例 1） | 黑盒（案例 2） |
|------|------|------|
| 接口发现 | 文档直接提供 | JS 逆向 + fuzz |
| 参数准确性 | 精确到字段名 | 需推断验证 |
| 测试覆盖率 | 高（文档覆盖的都能测） | 中（可能遗漏隐藏接口） |
| 耗时 | 较短 | 较长 |

> 有文档一定要放 `materials/`，效率差一倍以上。
